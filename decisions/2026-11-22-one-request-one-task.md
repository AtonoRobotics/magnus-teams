# One request is one task

**Choice.** A sub-agent is never listed among a person's tasks. `State::listed(task)` (`sub_agents.rs`) is the one rule: not a chat turn, and not a run in the sub-agent ledger. The task list, task search, Home, project task counts and lists, the control API's `tasks_for` and an admin's view of a person's tasks all use it. The sub-agents a task started, nested ones too, are shown inside that task: its full row carries `sub_agents` (built by `chat_thread::sub_agents_of`, the same builder as a chat turn's sub-agents entry), and the desktop draws them with the chat's sub-agents card.

**Reason.** The owner reported on 2026-11-22 that one autonomous task request resulted in many tasks being created. Each sub-agent is a run with its own task record, and the lists hid only sub-agents under a chat turn (decisions/2026-11-09-chat-does-the-work.md). So every sub-agent a task started was listed beside it, including each OpenWeb research compartment the agent now opens to browse (decisions/2026-11-22-autonomous-browser-navigation.md), and a task that fanned out showed up as many tasks. The spec calls sub-agents "child runs" a task starts, carrying its authority, not tasks of their own, and the chat decision already said a task's sub-agent "stays with that task".

**Changed test.** The scratch acceptance test `a_scheduled_run_uses_sub_agents` asserted that the person saw the run and its three sub-agents as four tasks. It now expects one listed task under the schedule with its three sub-agents inside it, and it finds the sub-agents' actions through that task's `sub_agents`.
