# Invites and status gate local sign-in (2026-11-07)

- #429 slice 2 is invitations with invited/active/disabled status: single-use 128-bit tokens (7 days, hashed at rest), an accept route that sets the password and activates, and status enforced on the local sign-in path. Reason: invites are the next spec unit after TOTP that stands alone, and the console Users slice needs this machinery underneath it.
- No record means active; an invite marks invited only someone with neither a password nor a record; a set password completes an invitation but never a disabling. Reason: an invite must never revoke working access (a resend that locks out), while setup by any path (accept or CLI) finishes the invitation; only an explicit switch restores a disabling.
- Status is checked after the password and before the code, and refuses uncounted. Reason: after keeps the timing alike, before keeps no `NeedsCode` from betraying a right password for someone turned off, and uncounted because the password was not wrong.
- Disabling ends live sessions at once (ids returned for the caller to record). Reason: the spec's "off means out within minutes", satisfied immediately at the switch; the per-request session check lands with the session-lifetime slice.
- The owner backup path and the provider path ignore local status. Reason: the backup is break-glass by design, and provider people are governed by the provider's own active flag until the cutover.
- Invites need a config person for now. Reason: sign-in still resolves people from the config; the local user store slice lifts this when people move out of the file.
