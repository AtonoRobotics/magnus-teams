# A wake no hibernation can cut off, a desktop started with the wake, and a deflated screen

The owner, 2026-11-11: "computer is very slow to wake up. It's very high latency." Spec rev 145, Lifecycle: "While it wakes, the client shows the last screenshot and the progress, never a start button."

**What was measured on the server.** The disk is the bottleneck. With the release runner building the desktop app on the same machine, the NVMe (a DRAM-less 512 GB drive, 78% full) wrote about 17 MB/s with each write waiting over a second, and the kernel's IO pressure stall stayed between 55% and 75% for minutes. Hibernating a 4 GiB computer writes its memory twice (Firecracker's snapshot, then the sealed copy) and a resume writes it once more: on that disk one hibernation took about seven minutes (21:09 to 21:17 UTC) and the next three to six. The fix for that is on the host: build releases elsewhere, or give the runner's unit a low `IOWeight`, so the computers' disk is not starved. computerd and Magnus now log every wake's and hibernation's steps, so the next measurement is in the journal.

**A hibernation and a wake of the same computer exclude each other.** At 21:09 the idle loop, working through a list of computers made before the hibernations ahead in it, reached a computer that a wake was booting. Its hibernate request waited for computerd's lock, then snapshotted the VM the wake had just booted; the wake's guest never answered, the wake failed, and the computer went back to sleep. Now a hibernation, the idle one or the person's, holds the same per-computer claim a wake does, so neither starts while the other runs; the idle loop checks again, holding it, that the computer is still running, unheld and idle; and a use that finds the computer going to sleep waits for it, then wakes it, with the wake's own time limit starting only then. Going to sleep is not shown as waking. Test: `computer::wake::tests::a_computer_going_to_sleep_does_not_wake_until_it_has_and_a_waking_one_does_not_sleep`.

**The desktop starts with the wake.** It used to start on the first screenshot or screen, so a person opening a computer that had just booted cold waited for XFCE after the wake. After a cold boot the kernel sets the look and then starts the desktop in the background; a resumed desktop is running already. Test: `computer::desktop::tests::the_desktop_starts_in_the_background_without_holding_the_command`.

**The screen goes deflated.** The guest's VNC server sends raw pixels, 4 MB for a full 1280x800 frame, and the client reads raw only. A client that can inflate (`DecompressionStream`) offers the WebSocket subprotocol `magnus.display.deflate` before `magnus.display`; the server then sends the screen through one zlib stream, fast level, flushed at every chunk so each can be drawn at once. A desktop's pixels shrink many times over. An older app or browser does not offer it and an older server does not choose it, so either side alone keeps working. The app carries the deflated bytes and says so with each chunk; the page inflates them. Tests: `computer::display::tests`, `desktop/tests/rfb-check.mjs`, and the app's `display::tests`.

**The client joins a frame once.** `rfb.js` copied everything it held on every chunk it was fed, so a 4 MB frame arriving in 1 KB pieces allocated 8 GB; it now keeps the chunks and joins only what one message spans. The app's base64 decoding of the screen is a plain loop instead of a call per byte.

**In the guest (with the next base image).** x11vnc ran with `-noxdamage`, finding changes by scanning the screen a few lines at a time; the desktop has no compositor, so the X server's damage reports are exact, and x11vnc now uses them. The guest's connection to x11vnc sends each key and pointer move at once (`TCP_NODELAY`). And every guest command waited a fixed 150 ms after it exited for output a background process might still write; it now waits only until its output is read, up to the same 150 ms, which every screenshot the agent takes saves. Tests: the guest's `tests`.

**Each takeover's screen is logged** when it closes: how long after the client asked the first frame began, and how many bytes came from the screen against how many were sent.
