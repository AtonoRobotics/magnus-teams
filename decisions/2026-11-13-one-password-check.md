# One password check that owns its lockout: `password_check::check`

**Choice.** Every typed password (app sign-in, the Admin step-up, choosing a password with a temporary one, changing it in Settings) is judged and counted in one place. `password_check::check(k, &Attempt { person, password, code, machine_code, via, app })` settles who keeps the password (the identity provider, or the server's own store for a person only it keeps, #429) and whether the person is known, and `Accounts::check_password` (`accounts/check.rs`) does the rest: which counter (`Via::Network`, `Via::ThisMachine`, or the owner's backup when a machine code comes under a provider), count before the provider answers, take the count back when the answer says nothing about the password (needs the code, its own page, or the provider is down), clear it on a right answer. It answers `Checked::{Yes, NeedsCode, MustChoose, Wrong, Locked(until), Elsewhere(polled), Unavailable(label)}`.

`locked`, `failed`, `succeeded`, `forgive`, the counter names and the `sign_in_counted*` checks are now private to `accounts`. Invitation links, which limit guessed codes per address rather than passwords, use `Accounts::guesses_locked(ip)` / `guessed_wrong(ip)`, which can only touch the `signup:<ip>` counter. The 429 "Too many wrong passwords. Try again after HH:MM UTC." with `retry_at` is `password_check::locked`, used by sign-in, choose, change and the step-up (which keeps its `{error: "locked", message}` shape). `passwords::kept_here` reads the same `provider_for` routing. The lockout code moved from `accounts.rs` (2268 to 2034 lines) and the protocol from `api.rs` (2246 to 2154) and `admin_app/guard.rs`.

**Drifts settled.**

- *Who is counted.* Sign-in counted provider attempts only for people in the config (`if ours`); the step-up counted every attempt. The reason for sign-in's rule is in `failed`'s own doc: only people of this server are counted, so guessing names cannot grow the table. That is kept and now holds everywhere: a known person (the config's or the store's) is counted, a stranger never is. The step-up loses nothing by it, as an admin with a session is always known.
- *The provider signing in someone else.* The step-up took `Done` for a different person as a wrong password; sign-in issued a session for whoever the provider named. The safer reading wins everywhere: it is `Wrong`, and stays counted. No working sign-in is lost: a name the provider would map to another account (an email it accepts) has never signed in here under that name, so sign-in sends it to the provider's page first.
- *A locked attempt.* The store here counted an attempt made while locked (hammering extends the lock, up to the longest wait); the provider path and the owner's backup returned the lock uncounted. Now every locked attempt by a known person counts, as the store's always did.
- *Fresh rules.* The provider path read the cached lockout rules; it now refreshes them first, as the store's checks did, so a change made in another process applies at once.
- *A stranger at the store.* The step-up's store check did not refuse a name neither the config nor the store keeps, as sign-in did (a former config person whose password row remains). It now does, for both, with the same work as a wrong password and uncounted; sign-in no longer runs a counted check for that dummy work.

Changing a password stays a password-only check against the store here (no authenticator code is asked there), but takes `Via` and gets its counter from the same place.

**Reason.** Five callers rebuilt the protocol (counter choice copied four times, provider-or-store routing twice, the 429 twice) and had drifted apart on who is counted and what a provider's answer means. One function makes the lockout one rule, and makes every drift visible as a decision instead of a difference. Nothing here is a new promise to users; each settlement follows the existing decisions (#429 local people, #508 lockout rules) toward the safer reading.

**Tests.** `accounts::check::tests`: one table through the function (provider yes, someone else, refused, needs code, its page, down; from this machine and the network; a stranger; the store yes, wrong, from this machine, ignoring a machine code, a stranger; the backup right, wrong machine code, wrong password, from the network, for a non-owner), each with the counts it leaves; the lockout's threshold, extension and lapse through the provider and the store; the backup's own lock. With the old behaviours put back (someone else's `Done` as yes, locked provider and backup attempts uncounted) all three fail.
