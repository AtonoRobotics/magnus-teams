# One answer to "may this work proceed": `halts::may_proceed`

**Choice.** Whether work may go on is decided in one pure function, `halts::may_proceed(state, Subject { person, agent, connector }, Phase)`, which returns the `Hold` that stops it: the server's kill switch, a switch below it (person, agent, connector), a paused agent, or the person turned off at the organisation's sign-in. Each `Hold` carries its own words (`said`, `refusal`, `reason`), so no caller rewrites another's text (the boundary's `replace("kill switch engaged", …)` is gone; the server's switch now says "the kill switch is engaged" everywhere).

The phases are what the code already did, made explicit:

- `Start` (new work): every switch, a pause, and a person turned off.
- `Continue` (a running run and its tool calls at the gate): every switch in scope. A pause lets what runs go on (K53), and a person turned off is not stopped mid-run: only their apps refuse.
- `Call` (a call through the person's own sign-in to one of their apps, in a run or a watched-read poll): every switch in scope and the person turned off.

`halt`, `holds_new` and `Kernel::refuse_new` are now thin callers of it. The boundary's last check before an app call, `poll_due`, the review sweep, the harness's list of watched apps and accepting a suggestion read it too.

**New: `create_run` refuses a person turned off.** `refuse_new` did not consult `turned_off`. A person turned off has their sessions ended and their schedules stopped "until they are turned back on" (`Kernel::turn_off`), and signing in again is what turns them back on, so nothing they can still do starts work. What could was work started for them by the server: a team routine they set up, a review, a sub-agent. The connectors spec says their apps "answer no calls for them until they are back", and the kill-switch decision reads a person's scope as "everything done for that person"; starting work for someone the organisation has turned off is the wider reading's opposite. Stopping is always safe, so new work for them is refused with `Halted` (a 409 at the API).

**Left alone, on purpose.** Sites whose question is not "may this work proceed":
- `kernel.rs` boot (the vault seals with the server's switch) and the vault's secret routes in `api.rs`/`connectors.rs`: a state of the server, not of one person's work.
- `api.rs::refused_by_kill_switch`: refuses new work before anything about it is recorded, where no person's scope is resolved yet; `create_run` then applies the full hold. Left to the API refactor running beside this one.
- `update.rs`: whether runs stopped by an update resume, which waits on the server's switch only.
- `push.rs::push_watches` and `push_subs`: whether a provider's push subscription should exist. A kill switch is released later without resubscribing; tearing subscriptions down on a switch would lose pushes after the release. The poll a push starts goes through the authorised read, which the holds refuse.
- `outcomes.rs` and `openers.rs`: a whole-server early return before a sweep; each run they start passes `create_run`.
- `kernel.rs::turn_off`: whether the turn-off event was already written, not a hold.
- `boundary::may_send` (the brokered fence): the server's switch only, read live inside the microVM call; the scoped switches are checked by the gate just before.
- Display and status reads (`control.rs`, `halts/agents.rs`, `admin_app/kill.rs`, `api.rs` health).
