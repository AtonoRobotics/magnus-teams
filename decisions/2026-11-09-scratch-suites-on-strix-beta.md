# The chat, standing authority and proactive suites pass again, on Strix Beta

Three end-to-end suites in `tests/scratch` failed on main at 89ea31f. Each failure was traced to the commit that caused it.

**Strix Beta could not run a task (most of chat.rs).** A task's contract checks run in the sandbox VM. The VM's guest kernel and image (`sandbox/out/`) are built, not checked in, and `ci/on-strix-beta.sh` copied the checkout without them. The VM exited at boot, the contract was refused, and every chat test with a task failed with "script exhausted". That was 6 of the 7. The browser check in the request-set test also failed on Strix Beta: `browser/node_modules` is left out of the copy. Neither is a product fault. `ci/on-strix-beta.sh` now does two things. When the checkout it runs from has a built guest, it refreshes one shared copy in `~/magnus-teams-ci/sandbox-out/`. It passes that copy to every command as `MAGNUS_GUEST_KERNEL` and `MAGNUS_GUEST_ROOTFS`. It also installs `browser/` with `npm ci` when the copy has no `node_modules`. A checkout without a built guest, such as a worktree, uses whatever copy is there.

**A chat task's restart test raced its outcome turn.** Since c357f32 (decisions/2026-11-09-outcomes-return-to-the-agent.md), a task's end returns to its thread as a new chat turn. In that turn the agent may start a task to finish the goal. The test's scripted model started a task on any first chat turn, so under load the outcome turn made a second task before the test counted them. The test is updated: only the person's message starts a task. The same change is made to the approval-at-restart test.

**The tasks list showed the server's turn text.** That same run showed something else. A task started from an outcome turn, such as a retry, was grouped in Tasks under that turn's text ("This turn is not a message from the person: ..."). The person never wrote those words, and the thread already hides them (89ea31f). A retry is now grouped under the message the person wrote, found back through the outcome turns (`outcomes::person_turn`). There is a unit test in `outcomes.rs`, and autonomy scenario 3 asserts each attempt's group title.

**Standing authority: the scripted model did not answer the independent checks.** Four tests had failed since 13e1fdf (Auto Review, decisions/2026-11-08-auto-review.md), well before spec rev 133. Their app writes under a grant are covered sends, and those go to Auto Review. Since 51ed3c3, Auto Review first asks the outgoing classifier. The test's model answered both checks as if they were tasks. A check that cannot answer asks the person, so nothing went ahead under the grant. The model now plays both checks, as autonomy.rs does (decisions/2026-11-09-autonomy-acceptance.md). The classifier finds nothing. Auto Review allows what a rule or grant covers (its document says "covered by a rule or grant") and asks about everything else. The grant still decides what goes ahead. A send or deletion the grant leaves out still reaches the person, and so do a payment (always the person, 5ab376d) and the Rule of Two (the floor, never Auto Review). No safety assertion changed.

**An app named "team" was refused outside a team thread.** With the checks answered, two tests still failed. Every `team__post` call was denied with "works only on a request made in a team thread". Since 3930c06 (team workspaces), any tool whose name starts with `team_` was taken for the workspace's own tool, and that includes a person's app named `team`. This was a real regression. Only a built-in tool (no `__`) is the workspace's now (`team::agent::team_only`, unit-tested).

**Proactive: the proposal's review is `task_id`.** c934718 added an assertion that read `items[0]["task"]`. An inbox item has always named its task `task_id` (`inbox::render`), so the assertion never held. It now reads `task_id`.
