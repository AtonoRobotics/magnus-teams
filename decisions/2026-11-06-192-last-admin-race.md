# The last admin stays when two changes come at once (2026-11-06)

- Every console change that can take an admin away (demote, turn off, delete, cancel an admin's invitation) takes one console-wide async lock (`Console::admin_removals`), reads the enabled admins from the provider under it, and keeps it until the provider has made the change. Reason: the check read the admin list separately from the change, so two changes aimed at the last two admins both saw two admins and both went through, leaving none (#192). Test: `admin_users.rs` `two_changes_at_once_never_take_away_the_last_admin` (on master: "round 0 (demote both): both changes went through and no admin is left: (204, Null) (204, Null)").
- The lock is in-process, and that is enough for the console's own paths: the console is the only Magnus code that changes roles, turns people off or deletes them at the provider (the kernel only reads), and it runs as one process per appliance (`magnus-admin.service`, `release/admin-on-appliance.sh`). The check inside the lock reads the provider, not a copy, so a change made outside the console before it is counted. Reason: the provider's state is what counts, and only the console writes it from Magnus. Test: `two_changes_at_once_never_take_away_the_last_admin`.
- Writers outside the console, such as Keycloak's own admin console used by someone with the provider's master credentials, are not coordinated: Keycloak's admin API has no conditional role removal or transaction to join. That is accepted, not closed. Reason: whoever holds those credentials can also make an admin again, so the organisation is never locked out by them, and the guard exists to keep the console from removing its own last way in. Test: none (no Magnus path to test).
- Cancelling any invitation takes the guard and the check, not only one read as an admin's before it. Reason: the role could change between that first read and the guard, and the check under the guard costs one provider read. Test: `an_admin_invites_someone_who_chooses_their_password_from_the_providers_email` (cancels an admin's invitation).
- Changes that only add admins (invite, promote, turn on) take no lock. Reason: one of them racing a removal can only make the check see fewer admins than there will be, which errs towards refusing. Test: `the_last_admin_stays_and_a_person_turned_off_loses_every_session_and_schedule`.
- No test-only pause between check and change. Reason: sending both requests through a barrier raced in all 12 rounds on master (every pairing of demote and turn off), so the test fails reliably without one, and the product carries no test hook. Test: `two_changes_at_once_never_take_away_the_last_admin`.
