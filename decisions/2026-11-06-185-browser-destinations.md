# The browser opens only public websites unless the owner allows an internal one (2026-11-06)

- The browser connects only to public internet addresses. Refused: loopback (127/8, ::1, `localhost`), unspecified (0.0.0.0/8, ::), link-local with the cloud metadata address (169.254/16, fe80::/10), private networks (10/8, 172.16/12, 192.168/16, fc00::/7), shared address space (100.64/10: CGNAT and Tailscale), multicast, and IANA's other special-purpose ranges (documentation, benchmarking, reserved, site-local, discard, IETF). An IPv4 address written as IPv6 (`::ffff:a.b.c.d`, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`) is judged as that IPv4 address, as `web_fetch` does since #196. Reason: navigation checked only the scheme, so a model could open `http://127.0.0.1:7701/`, the LAN or `169.254.169.254` and read them as web pages (#185). Tests: `the_browser_refuses_loopback_however_it_is_written_including_mapped_ipv4`, `the_browser_refuses_metadata_link_local_and_private_network_addresses`, `public_addresses_are_websites_and_special_purpose_ones_are_not` (tools.rs; on master: "the browser opened http://localhost:39447/ ... PRIVATE-CANARY", "the browser opened http://10.0.1.10:38647/ ... PRIVATE-CANARY", "Cannot find module .../browser/destinations.js").
- Every connection Chromium makes goes through an egress proxy inside the sidecar (`browser/destinations.js`): the page asked for, each redirect, and every image, frame, fetch and WebSocket a page starts, loopback included (Playwright adds `<-loopback>` to Chromium's bypass list). The proxy resolves the name once, checks every address, and connects to the address it checked; HTTPS and WebSockets are tunnels to that address. WebRTC may not send UDP around it (`--force-webrtc-ip-handling-policy=disable_non_proxied_udp`). Reason: a check of the URL before `goto` misses what the page itself requests, and Chromium would resolve the name again after a check made elsewhere (DNS rebinding); a proxy is the one place every request passes, and Playwright's `context.route` sees neither WebSockets nor the address Chromium finally connects to. Tests: `an_allowed_sites_redirect_to_a_private_address_is_refused`, `an_allowed_pages_images_frames_fetches_and_websockets_never_reach_a_private_address` (on master: "the browser opened http://127.0.0.1:33789/redirect: URL: http://127.0.0.1:37209/secret ... PRIVATE-CANARY"; "the page's subrequests reached the private address, left: 5, right: 0").
- A name is judged by the addresses it resolves to, and the connection goes to one of the checked addresses that is allowed; a name with none is refused. Reason: a public-looking name can point at the appliance's own host or LAN. Test: `a_name_resolving_to_a_private_address_is_refused_unless_the_owner_allows_it` (this machine's own name, which resolves to its LAN address; on master: "the browser opened http://strix-alpha:34449/ ... PRIVATE-CANARY").
- `navigate` refuses a non-public destination before the browser opens it, and a redirect the proxy refused fails the navigation with the same reason. Reason: the model is told why, instead of reading the proxy's refusal as a page. Tests: as above.
- An internal site opens only when the appliance's owner lists it in `[browser] allow`: a name or address, with or without `:port`, or a range (`10.1.0.0/16`). Default: none. Allowing a name allows whatever it resolves to, on that name only. Reason: DECISIONS names no internal site the browser is meant to reach; `web_fetch` has the owner's `allow_private_networks` switch, and a list lets the owner open one intranet site without opening the LAN, the host or the metadata address. Test: `a_name_resolving_to_a_private_address_is_refused_unless_the_owner_allows_it`.
- The existing browser tests (`tools.rs`, `kill_switch.rs`) serve their pages on 127.0.0.1 and now list it in `allow`. Reason: they relied on the browser reaching loopback, which is what #185 closes; their assertions are unchanged. Tests: `browser_navigates_clicks_types_and_screenshots`, `the_kill_switch_closes_every_runs_pages` and the others in `tools.rs`.
- When a name has several checked addresses, the proxy connects to the first that accepts a connection, in the resolver's order, without resolving again; an address that failed the check is never tried. This holds for plain HTTP and for HTTPS and WebSocket tunnels. Reason: Chromium falls back to the next address when one is unreachable, and a proxy that tried only the first would fail a dual-stack site whose IPv6 endpoint is down with 502 (review of #241). Test: `a_name_whose_first_allowed_address_refuses_is_reached_at_the_next` (without the fix: "page.goto: net::ERR_HTTP_RESPONSE_CODE_FAILURE at http://dual-stack.localhost:42623/").
- When an origin's response ends before its body is complete, the proxy cuts the browser's connection too, and a connection error after the headers does the same. Reason: piping the response left the browser's side open, so the page or its request waited for bytes that never came instead of failing (review of #241). Test: `a_request_whose_origin_disconnects_mid_body_fails_promptly` (without the fix: "the page's request still waited 20.686318s after the origin disconnected mid-body").
