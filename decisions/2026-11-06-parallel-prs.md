# Pull requests run beside each other (2026-11-06)

- Each pull request records its decisions as a file of its own in `decisions/` and what changed in `progress/`, named `<date>-<issue>-<slug>.md`, instead of adding lines to DECISIONS.md and PROGRESS.md (owner, 2026-11-06: "That would be better"). Reason: every pull request edited the same lines of those two files, so only one could be open at a time, and every small fix waited for the one before it to pass CI, be reviewed and merge. DECISIONS.md and PROGRESS.md stay as the record before this date. They are no longer hot files; the release and tag paths and live OAuth still are.
- Only master publishes to the installed apps: every merge to development (the owner's app) and to test (the testers'). No pull request publishes (2026-11-06). Reason: two open pull requests each published their own build to the owner's app, and each lacked the other's work, so the publish guard kept refusing one of them. Since #205, a pull request tested on build-box-beta published nothing, so whether a change reached the owner's app depended on which runner picked it up. A master build holds everything merged. Test: `ci.rs` `only_master_publishes_to_the_installed_apps` (fails on the previous workflow: "Development build for the installed apps publishes from a pull request").
- Master's publish to development first reconciles a pull request's build still there from before (review of #219): one closed without merging is given up (`MAGNUS_GIVEN_UP`), one merged is held by the commit it landed as (`MAGNUS_LANDED`). Reason: without that, `release/publish.sh` checks the old pull request's head against master, refuses, and exits 0 on development, so master would never reach the owner's app. On 2026-11-06 development held #205's build, which merged with a merge commit, so it would not have bitten, but a squash-merged or abandoned one would have.
