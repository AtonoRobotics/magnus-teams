# A run's kind is named once

**Choice.** `run/kind.rs` reads what kind of run a run is from the log, once: `RunKind::of(state, run)` (also `State::run_kind`, `Kernel::run_kind`). The kinds are a chat turn, an outcome turn (a chat turn the server started to return an ended task's outcome), a team request, a team routine, a task, a scheduled run, a review, a watch poll, and a sub-agent. A sub-agent's kind holds the kind of the run at the top of its parents (`SubAgent(Box<top kind>)`), so it is background, scheduled or team work exactly when its top run is (2026-11-10, sub-agents carry their parent's authority). Its own prompt and tools are a task's. A run the log does not hold reads as a plain task, which answers no to every question, as the old checks did.

Every question the kernel asked of a run's kind is a method on it, and the call sites ask it instead of reading the task's flags:

| Question | Asked by |
|---|---|
| `is_chat_turn` | the chat tools offered, the boundary's `misplaced` check, the refused run record, `show`, the person's grants in context |
| `converses` | the agent loop (a reply with no tool call ends the run) |
| `offers_records` | the run records a team run is not offered |
| `prompt` | the system prompt (`Prompt::{Review, Chat, Team, Task}`) |
| `is_background` | the halts, the computer, the kill switch, the suspend path, the failure notice (replaces `Kernel::is_background`) |
| `under_schedule` | `create_schedule` not offered, and `suggest` refusing a schedule, under a schedule |
| `unattended` | the unwatched ask's expiry |
| `in_team` | the harness's watched apps, a member's own sign-ins, the person's context, the memory pass, the playbook |
| `end_wakes_review` | the review wake after a run ends, and the backstop sweep (`State::end_wakes_review`) |
| `label` | Admin › Agents |

Where an ended run's outcome goes is `State::outcome_return(run)`: to the parent (a sub-agent), to its conversation (a task from one that is still there), or to the schedule's thread (a scheduled run), each only with the `returns_outcome` module. Only the last keeps its own failure notice (`OutcomeReturn::replaces_notice`): nobody is in a schedule's thread when it fails. `outcome_turn_follows` is now `outcome_return(..).is_some()`.

Removed: `Kernel::is_chat_turn`, `Kernel::team_talks`, `Kernel::converses`, `Kernel::is_background`, `Kernel::outcome_returns`, `Kernel::is_outcome_turn`. Lists that filter tasks by `Task::is_chat_turn`, and the team code that needs the `TeamRun` itself (`team_of`), stay as they are.

**Unchanged on purpose.** A scheduled run's failure keeps its notice; a team request is offered no `show` and no chat tools, and is told no grants; a team routine converses and runs under the team prompt as a team request does. These were already consistent across the old checks; the table test now states them.

**Fixed on the way.** Two checks read the run's own task where the 2026-11-10 decision says authority is looked up through the parent chain wherever it is checked:
- An ask from a sub-agent of a team routine was put to a person, though the routine has none to ask (asks.rs read `Task::background` off the sub-agent's own task). `State::asks_no_one` now asks the run's kind, so it is refused as the routine's own ask is.
- A sub-agent of a review left waiting on its person for anything but an ask was never ended, and its cards stayed up (`settle_background` read the sub-agent's own task). The selection is now `State::background_to_settle` in `background_work.rs`, which asks the run's kind, run and card alike.

Each has a test that fails on the old reading (`run/kind_tests.rs`), beside the table of every kind against every question.

**Left as they are, for the owner.**
- A team routine still counts as a team request where team work is counted; the `TeamRoutine` kind keeps that distinction available.
- `loop_deny` (proactive.rs) reads the run's own task for review and schedule, so a sub-agent of a review or of a scheduled run is not governed by the loop policy (`interrupt`, `suggest`) its top run is. Kept; whether it should be is a policy question.
- The instruction version a run is created with (kernel.rs) is chosen at creation from what is being created, not from the kind; it stays separate.

**Reason.** The kind was re-derived from the task's flags at each of some thirty call sites, each with its own idea of what a sub-agent, a team run or an outcome turn is. Two of them disagreed with the decision on sub-agent authority. One reading, asked by name, makes each rule one decision, and a new kind or question is one place to change.
