# The dropped-write test holds the log instead of racing it

**Choice.** `commit::tests::a_write_whose_caller_is_dropped_is_still_applied` locks `public.events` from a second connection (`LOCK TABLE ... IN EXCLUSIVE MODE` in an open transaction), polls the write until its append waits on that lock (seen in `pg_locks`), drops the caller, then releases the lock and checks the event is in the log and applied, and that the next write is seq 2.

**Reason.** Under heavy parallel load (3 runs of 48 test threads) the test failed with "the write finished before it could be dropped". That was the test's timing assumption, not a gap in the guarantee. `Writer::write` takes the write lock, builds the batch and spawns the append-and-apply task in one poll with no await between them, and a dropped `JoinHandle` does not cancel its task. So a caller dropped at any point either wrote nothing or left a task that finishes the append and the apply. The old test let the spawned task run free and raced to drop the caller before the task finished. On a loaded machine the task sometimes won, because it finished between the test's database check and its next poll. Holding the append in the database makes the drop land mid-write on every run. Three parallel runs of the whole lib suite at 48 threads each pass.

**Postgres connections under that load.** The test harness has no connection pool to size. Each test server holds about three connections of its own (the log, accounts, knowledge and recall each open one), and test-database setup adds a short-lived admin connection. Three runs at 48 threads peaked at 424 connections on Strix Beta's test Postgres, whose `max_connections` is 500. Every agent's runs share that Postgres, so "connect to Postgres" failures come from running out of slots there, not from a pool limit. Production limits are unchanged. If it recurs, the fix is the test host's `max_connections` (a host change), or a bound on test servers alive at once in each test process.
