# Cancel reports name the uncertain and the stopped (2026-11-06)

- Cancel reports gain `possibly_done`: intents still in flight (no result) or with an unknown outcome read as possibly done, irreversible first, beside the confirmed lists (#263). Reason: the spec says a cancel reports what had already happened; in-flight and outcome-unknown side effects may have happened and were silently dropped. The classifier is status-first (`unknown` wins over the error flag); failed and never-sent intents stay skipped.
- Both cancels share one per-run report helper, read from the run as it is after stopping. Reason: results recorded while the run stopped read done rather than possibly done; one helper keeps the task and schedule reports identical.
- A schedule cancel returns per-run reports (`runs`) and counts only runs actually stopped (`runs_stopped`), and DELETE now returns the report (200) instead of 204. Reason: the count included runs whose stop failed, and no per-run detail left the kernel; the desktop toasts ignore the body and tests accept any success, so 200 is compatible.
- No deterministic appliance test drives a pre-cancel unknown outcome: the only producers are crash recovery (which records after a cancel) and repeated unknown app failures (no test double produces them). Reason: the unknown mapping is pinned by unit test instead, and the appliance tests pin the plumbing with in-flight intents. A test double that fails unknown on demand would close this gap.
