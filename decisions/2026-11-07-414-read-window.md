# The window tracks reads, not wakes (#414)

Codex P2 on #411, confirmed: the window advanced only when a wake
started, so it held the last two wake-producing answers rather than
the last two reads. `{a},{b},{a},{c},{a}` woke on the final `a`
despite only single-read absences — contradicting the rule the #409
decision states (absent one read stays known). Every read now
advances the window, news or not; a no-news answer records itself
silently. A dropped wake still advances nothing, so it retries on
the next read.

That costs one small event per no-news watched read (a 1-minute
poll writes ~1440 a day per watch): the price of read-tracking,
precedented by schedules firing an event per run. Empty answers
count as reads: `{a},{},{},{a}` wakes on the return, two
consecutive absences. The #409 rule stands; only the mechanism was
wrong, and the test that locked the wrong behavior is restructured,
not weakened — it now asserts both halves (re-sighting silent,
consecutive absence wakes).
