# Local console posts bind by token, not Origin (2026-11-07)

- The local forms carry a single-use login token: the GET mints it into a host-locked cookie and a hidden field, and the POST takes it before credentials (#456). Reason: the merged Origin check refused every real browser login — probed locally, headless Chrome 152 submits forms from a no-referrer page with `Origin: null` and no Referer — while a test hand-crafting Origin stayed green. A token the attacker cannot read is immune to header quirks; Origin headers cannot bind under this console's policy, full stop.
- The binding consumes on every attempt and every re-render mints fresh; success clears the cookie. Reason: single-use per rendering keeps replay out, and a wrong password still retries smoothly.
- The login cookie is `Path=/`, asserted segment-wise by the e2e test. Reason: browsers reject `__Host-` cookies with any narrower path (probed: Chrome stores `Path=/` and drops `Path=/auth`), which would refuse every login as silently as the Origin bug; the test guards the contract instead of trusting it.
- The e2e test behaves like the browser and crafts no security headers. Reason: the Origin test's hand-made header concealed exactly the regression it guarded; the token test fetches forms and submits what they carry, like the page does.
- This replaces the merged #457 outright from master rather than reverting first. Reason: the endpoint is undiscoverable with zero users, and one cycle lands the correct state instead of two (a revert would briefly restore the CSRF hole it closed).
