# Computerd says its version, the server refuses plainly what it cannot serve, and root updates computerd from signed releases (2026-11-11)

On 2026-11-11 the teams server had updated itself to a release whose kernel sends `erase_volume`, but its computerd, which only root installs, was still the 9 November build. Computerd refuses a request it does not know with "bad request", and that reached the owner as the answer to Reset. Their computer stopped waking until computerd was installed by hand. The cause: nothing told anyone that computerd had fallen behind, and nothing could update it.

- Computerd answers a new request, `version`: the release it was installed from (a `VERSION` file the installer puts beside the program), the sha256 of its base image (`base.id`), and every request it serves. A computerd from before this answers "bad request", which the server reads as older than itself. Reason: the server needs to know what it is talking to, and the list of requests lets it refuse a new request without sending it.
- The server asks at start and every five minutes, and compares with the computerd it shipped: its own release version, and the base image hash signed with the release (`images.sha256`). Computerd is behind when its release is older, or when it is the same release on another base image. Reason: those are the cases where computers may fail to start or reset.
- While behind, Admin › Operations says "The computer service is older than this server: computers may fail to start or reset until it is updated", with the exact command that updates it, and Health notes it. Reason: an admin can act on it; a log line on the server reaches no one.
- A request computerd is known not to serve is refused before it is sent, and a "bad request" from computerd becomes a plain sentence saying the computer service needs updating. A reset that erases the files first checks that computerd surely serves `erase_volume`, and otherwise refuses without recording anything. Reason: the log recorded the erase before computerd was asked, and a person should never see "bad request".
- Computerd updates itself, as root, from the same signed releases the server installs: `magnus-computerd self-update`, run by `magnus-computerd-update.service` whenever `latest.json` changes in the release directory (a path unit) and hourly (a timer). It reads the package once into memory, checks its signature with root's own copy of the release key (`/etc/magnus/release.pub`, made once from the key built into the program root installed, never replaced by a release), the same check the server makes, and unpacks only what was signed into a root-only directory. The images are not in the package; their sha256 is (`images.sha256`), and each image is copied into root's directory and hashed there before it is used, so the bytes checked are the bytes installed. It installs only a release newer than the one installed, and runs the release's own installer from root's copy. Running computers are left alone, as by the installer. This revises the 2026-11-08 decision that computerd is updated only by the owner's script. Reason: computerd must keep up with the server without anyone remembering to, and root still trusts nothing the server's user can write: everything it installs is either signed or matches a signed hash. The server's user can make the update look again (by touching `latest.json`), which only costs a look.
- Turning that on takes one run of the installer by the owner, naming the release directory, which is also the command Admin › Operations shows. Reason: only root can install root's units and key.
