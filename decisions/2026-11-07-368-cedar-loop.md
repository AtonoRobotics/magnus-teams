# Cedar governs the loop's outputs (#368)

Split from #237: the loop core shipped with its outputs ungoverned.
Cedar now has `suggest`, `interrupt` and `act`, evaluated per
resource with the same org-permits, lower-layers-narrow layering as
control.

Resources are split by what the output spends. Suggest (observations
and proposals) and interrupt spend a person's attention, and their
inputs name no app the model does not control — deriving the
resource from evidence text would be governance the governed evade
by wording — so their resource is the person. Acts touch apps, so
theirs is the tool, as for execute. Kind-level filtering ("don't
suggest calendar stuff") stays in suggestion preferences where the
spec puts it; Cedar answers who gets loop outputs and which apps
the loop may act on.

Only loop runs are governed (review or schedule-originated tasks):
a person's own tasks proposing or observing are not proactive. A
denied suggestion or proposal fails that tool call, never the run.
A denied interruption degrades to an observation when suggestions
are allowed, mirroring the spent-budget path; a denied act fails
the call outright, never asked, as there is no one to ask
mid-sweep. The default permits all three, so existing behavior is
unchanged until an org narrows it.

Mechanically: the partition grows a third side (unqualified rules
stay tool-only, as before), the served schema gains the loop half,
and the unqualified-forbid guidance names the loop only when the
rule fails as tools but fits as loop: a Tool-scoped rule already
works as tools, and guiding there refused legitimate task layers
(CI on this PR).

Tests: `loop_policy.rs` — a suggest deny stops observations but not
the review, an interrupt deny queues an observation instead, an act
deny stops that tool call per tool (all three fail before: the new
actions do not validate).
