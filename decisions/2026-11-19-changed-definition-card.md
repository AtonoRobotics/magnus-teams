# A changed tool definition no model could screen goes to the owner on a card

## Choice
When a tool's definition changes and no model can screen the change (`tool_gate.rs`, verdict `unscreened`), the tool stays held and a `definition_change` card goes to the server's owner, who decides app tools as for the `app_tools` card (`crates/magnus/src/definition_card.rs`). The card shows what changed, compactly: the description before and after, each input added, removed or changed with its definition before and after, and the rest of the schema when that changed, each cut at 600 characters. It offers Accept the change or Disconnect. Accept records the definition the card showed as screened with the new verdict `accepted`, which pins it, but only while that definition is still the one held: one screened, accepted or changed again since is left as it is. Disconnect removes the app, as the `app_tools` card does. One card per definition, never a second while it is open. Connecting the app again still clears the hold as before; the card is the way that shows the change.

The proposal's alternative, screening with the default model when no screening model is set, is not done. `screen_definition` (`safety.rs`) would send the changed description to the working model, and invariant 1's `a_changed_tool_definition_is_disabled_and_hidden` asserts that no request to the model carries a changed, unapproved description, screening calls included. Doing it needs the owner: a `tests/invariants/` change that leaves out requests offering the `screen` tool, and the owner's view on whether the working model may judge definitions.

## Reason
Item 6 of `docs/proposals/2026-11-19-approvals-review.md`: holding the tool until the app is reconnected made reconnecting accept the change with nobody seeing it. The owner can judge a definition change better than the system when no model could: they see what the app now tells the agent. Accept pins only what was shown, so the card can never accept a later change nobody saw.
