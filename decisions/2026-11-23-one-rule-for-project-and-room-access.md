# 2026-11-23: One rule for who reads a project and who posts in a room

## Choice
1. **One read rule.** `Workspace::may_read(project, person)` (`team/knowledge.rs`) is the only answer to "may this person read project p": they must be in the workspace, and for a project, on its list. A project that has been removed counts as closed to everyone. `sees`, `sees_file`, tasks, search, sharing a message and the knowledge base all ask it; the second rule (`in_project`, which read a missing project as open to every member) is gone.
2. **A deleted project's channels are deleted.** Applying `ProjectRemoved` (an admin removing a person with `projects: "delete"`) now deletes the project's channels from the workspace, with their per-channel and per-message state, instead of untying them. Files and tasks still filed under the gone project stay closed to everyone by rule 1. The event kind is unchanged; only what applying it does changed, so replay gives the same state.
3. **One room-access check.** `routes::has_channel` is the one check that a person may read or write a room. Releasing a lane, steering it, sharing a whisper, posting a released contribution (by the owner or the lane watcher), starting a lane for a member, and adding or changing a routine all go through it. The second wrapper (`mission_routes::sees_room`) is deleted.
4. **One invite admission check.** `invites::admits` decides what an invite lets someone in as: nothing once its issuer is no longer on the server or in the workspace; never above the issuer's current role there; only `Guest` when the server holds the issuer to a guest's limits. The signed-in join, the link page (show and submit) and an accepted account invitation (`join_bound`) all ask it. A link or email invite a server guest makes is stored as a guest's from the start.

## Reason
A private project's channels, history, files and tasks fell open to the whole workspace when its owner was removed with their projects deleted, because one rule read "no project" as open while the knowledge base read a missing project as closed. Of the two readings for the channels, deleting them is the safer: the admin asked for the project to be deleted, and keeping them "closed except to workspace admins" would have shown a private project's history to admins who were never in it, which `may_read` already refuses for the knowledge base. Room writes, and invites, each had several paths checking less than the others; one check per question closes the gaps and keeps them closed as paths are added.
