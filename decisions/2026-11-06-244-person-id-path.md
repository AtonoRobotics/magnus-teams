# Every person ID maps to a user directory (2026-11-06)

- A person id maps to its `/users/` segment (`bundle::user_segment`): path-safe bytes stay (`-` doubles), every other byte is `-` with its uppercase hex, and `.`, `..` and empty escape instead of refusing or vanishing (#244). Two ids never map to one segment. Reason: user documents used the raw id in the path, whose rule refuses `@`, so a person with such an id could keep neither relationship memory nor user documents — and ids are unbounded (configured, or the provider's username claim), so widening the rule cannot cover `/` or `..`.
- The mapping is applied at the three places a segment meets an id: the write's ownership check and the frontmatter check compare the canonical mapping (frontmatter still names the raw id, so readers, erasure and the content owners are untouched), the write event's `owner_user` is the raw id, and `relationship::path` builds the mapped directory. A run that writes its raw id is refused naming its mapped directory. For plain ids the mapping is the identity: nothing changes. Tests: `bundle::tests::every_person_id_maps_to_one_valid_user_segment` and `relationship_memory.rs` `a_person_whose_id_has_at_and_dot_keeps_user_documents` (relationship round-trip plus a user document written and read through the tools; fails on the old code at the first write).
