# Seven kernel bugs from review: no unbounded waits, no dropped writes, no lost causes

1. **A provider's retry-after never holds a run asleep.** Before, an `Unavailable` error waited however long the provider's `retry_after` said (1e12 s would sleep for good). Now an unavailable provider and a usage limit are treated the same way: a retry-after within `LONGEST_BACKOFF` (32 s) is waited out, and a longer one pauses the task with a notice ("provider" or "usage_limit"), which the person resumes. This follows the loop's own comment ("a limit it says lasts longer persists, and pauses the task"). It is also the safer reading, because a paused task is visible and holds nothing, while a sleeping one looks like it is running. `run::agent_loop::retry_delay` computes the wait as a pure function, and the 500 ms base is a named constant.
2. **An egress audit row with a port outside u16 is left out and logged.** It is not shown as port 0. A port no proxy could use means the row is damaged, and showing port 0 would describe a request that never happened.
3. **The sign-in rate limit survives a poisoned lock.** It uses `unwrap_or_else(into_inner)`, as payments does. The counts are still valid after a panic elsewhere, and a panic on the sign-in path would lock everyone out. Its ten-minute window is now the named constant `SIGN_IN_BEGIN_WINDOW`.
4. **The computerd version record is written and read through a poisoned lock.** Before, a poisoned lock dropped the write, and a stale answer then gated reset and erase_volume.
5. **The sandbox's exec reply timeout saturates.** It is `timeout_s.saturating_add(EXEC_REPLY_GRACE_SECONDS)`. The sandbox's other bare durations (ping, boot, file request, check tools, sync) are now named constants as well.
6. **Minute limits from config saturate when converted to seconds.** A huge `idle_hibernate_minutes` or `max_run_minutes` means "no limit". A wrap would turn it into a short limit and hibernate or stop every computer at once.
7. **Deleting a generated connector is best effort, and its error keeps the cause.** Grants are revoked and rules removed even when the token cannot be revoked, because taking a permission away is always safe. A failure there is logged and the remaining steps continue. If the token could not be revoked, the connector is kept and the error carries the vault's reason, so the token stays visible and the person can try again. Removing the connector while its token lived on would leave a live credential with no record of it.
