# Relationship memory and recent messages in every run (2026-11-06)

- A person's relationship memory (tone instructions such as "fewer jokes", what they delegated, standing decisions) is one user-scope bundle document, `/users/<person>/relationship.md` (type `Relationship`, `scope: user`, `owner_user`), one note per bullet, written through the bundle's checks and versions (`bundle_write` for Magnus's run, the same event as the person's own `human:<person>` write for theirs). Reason: the owner's ruling (org-context.md, 2026-11-02) keeps it in their user memory under `/users/<user>/` and rules out a second store; the bundle already makes a person's own documents theirs alone (K2) and deletes their content with them. Test: `relationship_memory.rs` `the_person_sees_corrects_and_removes_their_notes_and_runs_follow_also_after_a_restart`.
- Magnus records, changes and removes notes with one dedicated tool, `relationship_note` (`add` a text, `change` or `remove` a note by its words), in app `memory`, so a chat turn may use it and it needs no contract, as for `memory_write`; the memory pass cannot. A run may write the document only through it: `bundle_write` to that path is refused. Reason: the narrowest write; the notes enter every run as the person's own words, so they get a check no other bundle document needs. Test: `a_tone_instruction_is_in_every_later_run_of_its_person_and_seen_by_no_one_else` (a task's `bundle_write` to the path is refused).
- `relationship_note` refuses a run that has read untrusted or private content, saying the person can say it again in a new conversation or add it in the app. Reason: a note is carried into every later run untainted; one written after reading a web page or someone's mail could launder that content, or an injected instruction, into all of them. Test: `a_run_that_read_outside_content_writes_no_note` (a chat turn reads a web page, then its note is refused).
- Every run and chat turn of the person carries the notes in its system context, after the instructions, under "Relationship memory: how this person wants you to work with them"; with none, nothing is added. Each model call logs the notes' version (`ContextRef.relationship`), as it logs the instructions' version. The kernel's own passes (memory pass, verifier, knowledge extraction) have their own prompts and carry neither the character nor this. Reason: the owner's ruling (always in context, by code, not searched for), and DECISIONS "Identity and characters" for the passes. Tests: `a_tone_instruction_is_in_every_later_run_of_its_person_and_seen_by_no_one_else` (a later chat and a task of hers carry it; the call logs version 1; Bob's run does not).
- The person sees, corrects, adds and removes their notes in the app (Settings, Data and privacy, "How Magnus works with you") through `GET`/`POST /v1/relationship`, which answer only for the signed-in person. Reason: behavior spec ("Users adjust Magnus by telling it", "never surfaces to another user"); Data and privacy is where a person already manages what is kept about them, and a new Settings tab would change the section list the app test checks. Test: `the_person_sees_corrects_and_removes_their_notes_and_runs_follow_also_after_a_restart` (the API; the view itself is untested in the UI).
- No admin reads a person's own documents: the console's version and change reads (`/v1/admin/knowledge/version`, `/activity/{seq}`) and its undo now refuse `/users/<user>/` paths, as the list, document and write already did. Reason: they looked a write up by path or sequence alone, so an admin could read, or undo, any person's user memory. The owner's reads of a person's data (tasks, chats, memory entries) never included bundle documents. Test: `a_tone_instruction_is_in_every_later_run_of_its_person_and_seen_by_no_one_else` (every console read and the undo, and the owner's data reads, show nothing of it; without this change `/v1/admin/knowledge/version` returned Carol's note).
- Erasing a person removes their user-scope documents from the state as well as their content from the store, so after a replay too the next person known by their name starts with none; the path keeps counting versions. Reason: the owner's ruling on erasure ("their user-scope documents and versions"); before, the state kept the document with its content gone. Test: `erasing_a_person_removes_their_relationship_memory` (against Keycloak; without this change the erased person's document was still at version 1).
- Each run sees Magnus's recent messages to the person from their other conversations: its answers and its tasks' results that ended before the run started, newest first, recalled for them through their wall as their threads show them (deleted and hidden entries out), only those written by a run with no untrusted or private taint, and at most 16KB (`bundle::INDEX_CAP`); the notes are capped at the same size. Reason: the behavior spec ("Magnus can see its recent messages to this user and does not reuse a joke or a turn of phrase") gives no count, and its purpose is the words, so the limit is on their size, taken from the bundle's own limit on what every run carries (K9); messages from a tainted run would taint every later run; ending before the run started keeps its context the same at every call (C1). Test: `a_new_run_sees_its_recent_messages_to_the_person_from_other_conversations_and_none_to_anyone_else`.
- Each model call logs as its instructions the run's instructions by name, hashed with exactly the system context it was sent (`run::sent_version`), the person's relationship memory and recent messages included; the run's config keeps the instructions' own version, and the developer view compares that with the build. Reason: CI on #245 (run 42160635846) failed `character.rs` `magnus_speaks_as_itself_in_its_character_on_every_call_and_the_log_says_which`: the logged hash no longer named the prompt Magnus spoke with, against "Identity and characters" (the product was wrong; the test unchanged).
- `content_walls.rs` `a_persons_memory_is_recalled_from_the_content_store_for_them`: its script answered with the whole model request when it meant the memory search's result, so the request's recent messages (an earlier answer naming the fact as it was) failed it. A test bug: the answer is now the search's result only, and the test asserts the same.
- Recent messages are chosen straight from the person's runs, newest first, stopping once their text fills the budget (`chat::recent_runs`), not by rebuilding every conversation of theirs on each model call. Reason: review of #245 (each call scanned every task and cloned every run per conversation). Test: `chat::tests::the_recent_messages_are_the_newest_and_their_choice_stops_at_the_budget` (fifty 1KB answers: the newest sixteen, the run's own conversation left out; without the stop all forty-nine come back).
- Each recent-message bullet counts its date and marker against the 16KB budget, and nothing more is added once not one more character fits. Reason: review of #245 (with less left than the next character, empty bullets were added without end). Test: `relationship::tests::the_recent_messages_never_pass_the_budget_whatever_is_left`.
