# The appliance keeps its own people, and sign-in resolves them (2026-11-07)

- #429 slice 5 stores local people in `accounts/people.json` as `{id: {name, email?}}`, with `add/is_local/local_person/local_people/remove_person` on `Accounts`. Reason: identity is the last config-only piece — passwords, codes, status and roles already live beside it — so the directory lands in the same files-next-to-passwords shape the earlier slices set.
- A person id is 1 to 64 letters, digits, dots, dashes and underscores; adding refuses dupes and anything wilder. Reason: ids travel through URLs, JSON keys and shell args, so the narrow rule keeps every use safe without escaping at each site.
- Removing drops every local trace — record, password, authenticator, used code steps, status, role, invites, live sessions and failure counters — and refuses an unknown id or the organisation's last enabled admin. Reason: removal is the offboarding path, so a leftover trace is a way back in; the last-admin guard matches the demote/disable guards, since removing strands the same way.
- Sign-ins resolve the config first and the local store after (`resolve_person`, split out so tests reach it without booting a kernel); a local person arrives with no token, no groups and no roles. Reason: config-first keeps every existing deployment byte-identical, and a local person starts a plain member with nothing to escalate from — their console role overlays separately, as slice 3 set.
- The API signs a local-only person in from the local store even with Keycloak live, and accepts their invites; config people keep the provider path even with a local namesake. Reason: dual mode by person, not by flag — Keycloak never heard of local people, so sending them to it could only refuse, while nobody already on the provider moves.
- The owner manages local people from the shell (`person-add`, `person-remove`, and the five existing person commands now accept local people). Reason: the appliance-owner path the earlier slices built stays the way in until the Users panel (slice 6) offers it on screen; `person-add` refuses config ids so a record that could never resolve is never made.
- Local people have no API tokens and no machine-code backup; the kernel `Person` carries no email (the console reads `LocalPerson` for that). Reason: tokens and the backup are owner-scoped by earlier rulings, and email only matters where invites are sent — nothing resolved gains a field it never had.
