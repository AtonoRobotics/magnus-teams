# A catalog connector is withdrawn by a signed list beside the update feed; manifests stay release-bound

**Choice.** The connectors spec's Lifecycle asks that "appliances disable the connector, revoke its connections and tell affected users in their Library" when a connector is withdrawn. The catalog's manifests are compiled into the server (`catalog.rs`), trusted because the release is signed, so until now the only way to take one out was a new release. Now:

- **The list.** `catalog/withdrawn.json` in this repository (`{"serial": N, "withdrawn": [{"id", "versions"?, "reason"}]}`, empty by default) is published by `release/publish-withdrawals.sh` into `<updates>/catalog/withdrawn.json` with `withdrawn.json.sig`. The release workflow's publish job runs it before fetching the build, and it can be run by hand on the server for a withdrawal that should not wait for a release. It is signed with the release key by the same mechanism as a release package (`tauri signer sign --app-version`), the bound version being `catalog-withdrawals.<serial>`, so neither a release's signature nor another list's passes for it.
- **The server** (`catalog_withdrawal.rs`) reads it at start and on the update check's cadence (`[updates] check_minutes`), whether or not updates install automatically. It verifies it with `update::verify` and the configured release key. An unsigned list, one that does not verify, or one with a serial older than the one applied changes nothing: the last good one stands, recorded in the log (`catalog` events). A missing list changes nothing either. The same serial again is a no-op.
- **Applying it.** A withdrawn connector whose compiled manifest's version is in the named range (`versions`, a semver requirement; none, or one that does not parse, is every version) is left out of `Kernel::all_connectors`: it is in no one's Library, no run reaches it and no admin can turn it on. Every person's connection to it is revoked at the provider and deleted through the same path as Disconnect (`Kernel::disconnect`, now naming who ended it: `kernel:catalog` here); the old shared sign-in, if any, is revoked and deleted too. Each person who had a connection first gets an inbox notice naming the connector, the reason and the provider page where Magnus's access is removed; the log records that they were told, so a later look (after a crash, say) ends what was left without telling them twice.
- **One-way.** A withdrawal stands until a later list (a higher serial) leaves the connector out, or a release ships its manifest at a version outside the range. Restoring it reconnects no one: people sign in again.

**Manifest updates stay release-bound.** A manifest's content (its tools, classes, scopes, endpoint) changes only with a signed server release. The release is installed after running tasks finish their current step (`update.rs`), which is when no call is in flight; brokered servers are named by image digest (`catalog::kind_problem`). There is no separate manifest feed: it would need a second signed artefact for what the release signature already covers, and the withdrawal list is the only thing that must move faster than a release. Local add-ons updated through the desktop app's updater are not built.

**More access in a newer manifest.** A newer manifest that asks for a scope existing sign-ins lack asks through the existing scope card the first time a tool needs it, when the provider answers that call with a scope challenge (`insufficient_scope`): the call becomes a Connect card for the added scope and goes through once approved (`agent_apps.rs` `a_call_that_needs_more_access_asks_for_it_with_a_card_and_goes_through_once_approved`). Magnus does not itself compare a sign-in's granted scopes with a newer manifest's; a provider that refuses without a challenge shows the call's error instead.

**Reason.** The safety need is to stop a connector everywhere between releases; the trust the catalog already rests on is the release key, which the server already holds and verifies with. Reusing it adds no key, no service and no new promise. The serial stops an old list being replayed to bring a connector back. Telling before revoking, recorded, keeps the notice to one per person per withdrawal across restarts.

**Not done.** The Library does not yet draw a card for a withdrawn connector: people learn of it from the inbox notice, and the connector disappears from the Library. A provider push subscription for the connection is not ended explicitly (the connector is already withdrawn when Disconnect runs); it lapses with the revoked tokens. The spec's staging and production catalogs and a catalog key of their own (connectors spec, Review and publishing) are not built; this list is signed with the release key until they are.
