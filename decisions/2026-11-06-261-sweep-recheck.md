# No run for a schedule cancelled or paused while starting (2026-11-06)

- The sweep rechecks, immediately before `create_run` with no await between, that the schedule still exists and is not paused, and skips the firing otherwise (#261). Reason: a cancel or pause landing during the title/words recalls previously started a run of a removed or paused schedule, which the person could no longer cancel through the schedule. Full atomicity (recheck under the write lock with the append) would need a locked `emit` variant; the recheck matches the codebase's read-then-emit convention (`cancel_schedule`, the kill-switch check) and closes the reported interleaving. The residual sync-only window between the recheck and the write-lock acquisition is noted, not fixed here. Test: `schedules.rs` `a_schedule_cancelled_while_starting_gets_no_run` (fails without the recheck: "a run started for the cancelled schedule").
- The interleaving is driven by a debug-only sweep gate (`<state_dir>/sweep-gate`, acked by `<state_dir>/sweep-gated`), the same pattern as `crash-after`: zero release cost, no-op when the file is absent. Reason: the cancel must land strictly between the due-snapshot and the creation; a timing-based test would be flaky by construction, and appliance tests are HTTP-only with no `Kernel` seam for a stale snapshot. A gate that never trips fails the wait, so the tests cannot pass vacuously.
- A failed recheck skips silently: no `ScheduleSkipped`, no notice. Reason: events for a removed schedule apply as no-ops but pollute the log, and stamping a paused schedule skipped every tick would spam it; paused schedules are not due (`next_due`), so the recheck only trips on a pause that landed mid-recall. On resume the schedule fires normally (`ScheduleResumed` resets `last_fired`), pinned by `a_schedule_paused_while_starting_gets_no_run_until_resumed`.
