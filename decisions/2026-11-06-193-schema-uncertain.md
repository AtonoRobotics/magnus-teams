# A call made whose answer breaks its schema is a bad answer, not a failure (2026-11-06)

- When a brokered tool has run and its answer does not match its output schema, the kit says so in the result's outcome (`_meta["io.magnus/outcome"] = "bad_answer"`), next to `unknown` and `needs_scope`. It does not leave it to the message text. A call refused before it ran (its input, no token) still carries no outcome, which means nothing happened. Reason: the provider may already have done what it was asked, and the kit cannot tell a write from a read, so it reports what it knows and the appliance decides. Test: `kit.rs` `an_answer_that_breaks_its_schema_says_the_call_was_made` (fails on master: `left: Null`, `right: Object {"io.magnus/outcome": String("bad_answer")}`).
- The appliance turns that outcome, and its own check of the answer failing, into `CallError::BadAnswer`, never an ordinary error result. Reason: the appliance checks the answer again in case the server does not, and that check also runs after the call was made. Test: `brokered.rs` `a_write_whose_answer_breaks_its_schema_at_the_appliance_is_unknown_never_sent_again`, against a test-server tool (`send_unchecked`) whose answer skips the kit's check (fails on master: "the write reached the provider again after its answer broke its schema: [("/json/read", "Bearer at-4"), ("/json/write", "Bearer at-7"), ("/json/write", "Bearer at-7")]", `left: 2`, `right: 1`).
- At the boundary, a bad answer from a tool classed `read` is an ordinary failure, and from any other class it takes the existing unknown-outcome path: reconciliation asks the person ("may or may not have happened. Send it again?", reason `unknown_outcome`), and nothing is sent again without them. Reason: a failed write invites the model to try again, which duplicates the effect. A read has no effect to duplicate, so it stays a plain failure. Test: `brokered.rs` `a_write_whose_answer_breaks_its_schema_at_the_server_is_unknown_never_sent_again` (fails on master the same way: two writes reached the provider). Both tests also check that the read's bad answer is an ordinary failure and the run goes on.
- Remote MCP connectors are unchanged: the appliance does not check their answers against an output schema, so nothing there turns a call that was made into a failure. Reason: the only output checks are the kit's and `brokered.rs`.
- The Gmail, Calendar, Chat and Slack images were rebuilt because the kit changed, and their manifests name the new digests. Each digest came out the same from a second build in a fresh target directory. Manifest versions stay as they are, as in the 0.2.5 image rebuild (6b30563), since the tools and manifests did not change. Reason: a manifest names the image built from its commit. Test: the image checks in `gmail.rs`, `calendar.rs`, `google_chat.rs`, `slack.rs` and `brokered_image.rs`.
- The appliance's own message about a bad answer is cleaned of the call's token before it goes anywhere, as the kit's outcome messages already were. Reason: the check names property names it did not expect, and a provider can echo the token as one; the unknown-outcome path logs the message. The test server's `send` schema now refuses extra properties, so the check names them. Test: `brokered.rs` `a_bad_answer_that_names_the_token_never_shows_it` (without the cleaning, the token is in the appliance's log).
