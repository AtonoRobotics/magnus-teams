# Asana ships on a fixed loopback redirect; Shopify is written and held until Magnus has client ID metadata documents

**Asana: the choice.** `catalog/asana.toml` is a remote connector to Asana's V2 server, `https://mcp.asana.com/v2/mcp`. It signs in through Alpha Vector's own MCP app with Asana (`registration = "preregistered"`, provider `asana`, confidential) at one fixed loopback redirect, `http://127.0.0.1:17322/callback`, with PKCE. All 44 tools the server lists are classed: 26 read, 3 reversible_write, 13 irreversible and 2 prohibited. The client ID and secret are the repository's `ASANA_CLIENT_ID` and `ASANA_CLIENT_SECRET`, provisioned by the release. `catalog/registrations.toml` names no Asana client ID, so `Client.client_id` is now optional. A provider with no catalog ID is ready only once an ID is provisioned. The provisioning step prints "set" or "not set" for that ID, never its value.

**Asana: the reason.** The V2 server does not take dynamic registration ("Dynamic client registration is not supported with Asana's V2 MCP Server", Asana's integration guide). The V1 server at `/sse`, which did take it, was shut down on 2026-05-11. A registered client is therefore the only way to connect. Asana matches the redirect exactly. `docs/remote-access-and-relay.md` puts Asana's switch to the relay's one callback at the relay cutover. Until then, a client can work only at an address the desktop can catch, and Asana's OAuth guide allows a `127.0.0.1` redirect when the sign-in uses PKCE (S256). Magnus always sends PKCE, and Asana's metadata offers S256. A fixed port is what Slack used before its https callback (DECISIONS.md), and the desktop already listens on a manifest's fixed loopback `redirect_uri`. 17321 is Slack's handoff, so Asana takes 17322. At the relay cutover the app's redirect becomes `https://pyrallon.ai/v1/connections/callback`, and the manifest drops `redirect_uri`. The catalog names no Asana client ID for two reasons: magnus-teams registered this client, and the catalog's IDs are shared with the magnus-claude lineage (2026-11-10-provisioned-client-ids.md). A per-deployment ID belongs in the vault.

**Asana: tool classes.** Writes that reach other people are irreversible, as GitLab's are: creating or updating tasks and projects (assignees and followers are notified, and `update_project` can make a project public or change its members), comments, status updates, deletes, and table schema changes (removing a field can lose its values). Marking the person's own Inbox notifications read is reversible_write, reaching only the person. So are table records, which can be changed and changed back without notifying anyone. `create_task_preview` and `create_project_preview` are prohibited. They draft into an interactive view in which the person creates the task with a click, Magnus shows no such view, and a creation from it would bypass Magnus's approval. `create_tasks` and `create_project` do the same work and ask first.

**Needs the owner.** Add `http://127.0.0.1:17322/callback` as a redirect URL on the Asana MCP app whose ID and secret are `ASANA_CLIENT_ID` and `ASANA_CLIENT_SECRET`. Until the app has that redirect, Asana refuses the sign-in.

**Shopify: the choice.** Shopify's own server for running a store is `https://setup.shopify.com/mcp`: server `shopify-mcp-server`, streamable HTTP, POST only, 37 tools including Admin GraphQL query and mutation tools. `catalog/shopify.toml` classes all 37: 22 read, 3 reversible_write, 6 irreversible, 5 financial and 1 prohibited. Anything that sets a price or puts priced products on sale is financial, and so is the raw Admin mutation tool. It is held out of the shipped catalog (`HELD` in `catalog.rs`'s tests). There it is checked like every shipped manifest, with `registration = "cimd"`, and shipped nowhere.

**Shopify: the reason.** Its authorization server, `https://setup.shopify.com/auth` (probed 2026-11-10), has no registration endpoint. It advertises `client_id_metadata_document_supported: true` and token endpoint auth `none`. A plain client ID is passed on to admin.shopify.com, but only with a redirect on Shopify's own allowlist: a loopback redirect is refused with "redirect_uri is not in the allowed origins list", and claude.ai's is accepted. Magnus therefore cannot sign in today. It would need either a client ID metadata document, published at a public https address Magnus's server controls, or Shopify allowlisting the relay's callback. Magnus has no client ID metadata documents (docs/connectors.md), and publishing that document is a host change. Shipping the manifest now would put a card in every Library that fails on every click. The repository's `SHOPIFY_CLIENT_ID` and `SHOPIFY_CLIENT_SECRET` are a Shopify app client. That client fits the Admin API's per-store OAuth, not setup.shopify.com, so nothing provisions it. A brokered connector over the Admin API was considered and rejected for now. Shopify's official server already covers the store owner's admin work, and a brokered one would need per-store hosts (`<store>.myshopify.com`), which a manifest's exact host list cannot name.

**Shopify: the plan.** Build client ID metadata documents: the server's client ID becomes the https address of a JSON document naming Magnus and its redirects, and the provider fetches it. Then publish the document, after checking that Shopify accepts a loopback redirect named in it, and move `shopify.toml` into `SOURCES`.
