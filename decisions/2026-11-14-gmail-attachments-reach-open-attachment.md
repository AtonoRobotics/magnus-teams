# Files from outside reach the agent's work, rebuilt clean, with no person asked

**What happened.** A run asked to make a flier from six JPEGs in an email. Gmail's tools gave only the file names, `open_attachment` answered "this task has no attachment from outside called image0.jpeg", and the run stopped. The kernel lifts an attachment out of a mail result only when the result carries its bytes as `data_b64`. No mail connector ever sent them, so the path from 2026-11-08 ("Attachments from outside") had never been reachable from mail. Even once reachable, a picture opened only as its file type, and the file could reach the work only through the person's save.

**The owner's rule (2026-11-14).** "The attachments and emails must be handled securely and autonomously. This is pointless if HIL has to get involved with the most basic functions." And: "All file types need a secure and safe solution for being downloaded and used by an agent."

**Choices.**
- Gmail gets `get_attachment` (message id and file name, class `read`). It returns the bytes as `data_b64`, so the existing lift keeps them out of the model's text and `open_attachment` finds them. It looks a part up by file name, not attachment id, because Gmail's ids change from one read to the next. The message's `attachments` list is unchanged: send_draft's read-back compares it with the sent message, and an id in it would never match.
- The login-code filter and secret redaction now run after the lift, never on the bytes. Run over base64, the filter found "codes" (4 to 10 characters, half of them digits, on a line that says "pin" or "otp") and damaged the file. A photo's base64 almost always holds such runs.
- `open_attachment` shows a picture to the model: the default extractor makes a smaller JPEG, the first of 1024, 768 or 512 px whose base64 fits under the guest's 200,000-byte output limit, sent as `image_b64`. The tool is labelled untrusted, so the inbound screen checks the picture as it checks screenshots. A picture's media type is read from its first bytes (`/9j/` is JPEG); screenshots stay PNG.
- `import_attachment` puts a file from outside into the run's workspace with no person asked, by content disarm and reconstruction. `attachment_rebuild.py` runs in the attachment's own sandbox (no network, nothing of the person's) and rebuilds each kind from its content alone:
  - a picture from its pixels (PNG where it may be transparent, else JPEG), at most 4096 px a side;
  - a PDF re-rendered from its pages by `pdftocairo` (no JavaScript, forms or embedded files);
  - a Word, Excel, PowerPoint, RTF or OpenDocument file re-saved by LibreOffice in the macro-free format of its family (`.docm` becomes `.docx`);
  - text, data and code as clean UTF-8, with `.txt` after anything a system runs by its name (a shebang, `.sh`, `.bat`, `.ps1`, `.js`, `.py` and the like);
  - a zip, tar, gzip, bzip2 or xz archive unpacked there with no links, no paths out (`..` and absolute parts dropped), at most 500 files, 512 MiB and three levels deep, each member rebuilt by these same rules.
  
  Only the rebuilt copies are read back. The kernel checks each path again (plain parts only) and writes it under `/workspace/from_outside`, and no file is executable. The original never enters the workspace. Invariant 2's attachment test still holds: opening does not import, and the raw file reaches the person's computer only through their save.
  - audio re-encoded to MP3 and video to MP4 (H.264 and AAC) by ffmpeg, the media streams alone: no metadata, chapters, subtitles or attached data;
  - a 7z or RAR archive read one entry at a time to memory with `7z e -so`, so the archive writes nothing to disk and no entry can be a link or land anywhere; links are left out.
- A program (ELF, PE, Mach-O, MSI, JAR, APK, disk images and the like) never comes in. It is said to be left out, and `open_attachment` still reads it. No agent task needs to run a program sent by a stranger.
- A kind with no rebuild in the sandbox image (fonts, databases, formats it does not know) is refused, by `import_attachment` and by `open_attachment` alike, as a program is (owner, 2026-11-14: "If the agent can't read the file there is no reason to download or open it"). An earlier version copied such data in unchanged and never executable. The rebuild program alone decides the kind (`rebuild.py --kind`), so the two tools cannot disagree. An archive's unreadable members are left out and named; its other members still come in.
- The sandbox image gains `ffmpeg` and `p7zip-full` (owner, 2026-11-14). The computer image does not: its packages stay the minimal set, and `sandbox/test_images.py` now checks that every program the rebuild runs is in the sandbox image. RAR needs p7zip's non-free codec, which Debian leaves out, so a RAR archive the free codec cannot read is said to be left out.
- An attachment is fetched only when the agent asks for it (owner, 2026-11-14: "not automatically download every attachment if the agent doesn't need to read it"). Gmail's `get_message` downloaded every attachment of every message it read, to digest them for the send check. Only mail the person sends is checked against its draft, so the digest is now made only for a message labelled `SENT` or `DRAFT`. Reading received mail lists attachments by name, and `get_attachment` fetches only the one asked for.

- **A fetched attachment is a temporary file** (owner, 2026-11-14: "Attachments should not be saved locally unless necessary. They should be a temporary file that is deleted automatically when complete. Ideally only what is needed from the attachments."). Before this, the lifted bytes went into the `tool_result` event's data, so every fetched file would have stayed in the append-only log and its backups. No release had a mail connector that sent bytes, so no log holds any. Now:
  - The event log records a fetched attachment by name, type, size and SHA-256, never its bytes. The mailbox keeps the original.
  - The bytes are held in memory (`attachment_hold.rs`) for the run that fetched them only. They go when the run ends (`run_end.rs`, beside its sandbox and browsers), after an hour, or oldest first past 1 GiB, whichever is first. A restart drops them too. A run that needs one again fetches it again.
  - Everything made from them is temporary as well. The attachment's own sandbox is destroyed after each open or import, and the clean copies live in the run's sandbox, which is destroyed when the run ends. What lasts is what the work needs and the person keeps: the text the agent read (it is the run's record) and the files it delivers.
  - Files a task is given at its start (`from_outside`) are the task's inputs, kept like an upload: the person can save one after the run (invariant 2), and they go with the trash, purge and erasure rules.
  
  This follows the research on best practice: data minimisation and storage limitation (UK GDPR Article 5(1)(c) and (e), ICO guidance: keep personal data no longer than needed, and delete what is no longer needed); ISO/IEC 27701's control on temporary files (they can hold personal data long after the task, so delete them when the work ends); and content disarm and reconstruction (OWASP File Upload Cheat Sheet). The pattern is to process in memory, delete right after, keep metadata for the audit, and re-fetch from the source.

**Not here yet.** Outlook lists attachments without their bytes and needs `get_attachment` too. The desktop still has no Save button for keeping the original.
