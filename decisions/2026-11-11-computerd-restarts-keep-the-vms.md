# A snapshot fits the base image its VM booted from; computerd restarts keep the VMs and clear what stopped ones left

Spec rev 145, Computer state: "Rebuild path. Boot the current base image, attach the user volume, restore the overlay snapshot if it was made on this base image, otherwise replay the manifest from its verified, cached installers." And: "Computer VMs outlive the Magnus server process, so an update does not stop them."

**What went wrong on the server, 2026-11-11.** A computer booted at 18:04 UTC on the fluxbox base image. The XFCE base image was installed under it at 18:09; the running VM kept the old image, as it should. It hibernated at 18:46, and `hibernate` labelled the snapshot with the base image installed *then*, the new one, not the one the VM ran. At 20:13 the wake found the label matched and resumed it: the old desktop, on a machine whose base image is XFCE, with the new image linked under a memory that expected the old one.

**A snapshot is labelled with the base image its VM booted from.** That is recorded in the computer's `meta.json` (`overlay_base`) at every cold boot, and a resumed VM keeps it. A wake resumes only when the label and the boot record are both the installed base image; otherwise it discards the snapshot and boots cold on the current base, keeping the user volume, and replays the manifest when the overlay is new. Checking the boot record too also catches a snapshot an earlier computerd mislabelled, so the fix needs no step on the host. Test: `computers::snapshot::tests::a_vm_that_booted_on_the_old_base_image_wakes_on_the_new_one`.

**A computerd restart keeps the VMs and adopts them.** The jailer daemonizes every VM into its own cgroup (`/sys/fs/cgroup/magnus-computers/<id>`), so a firecracker's parent is always process 1: that is not an orphan. computerd reads what runs from those cgroups, never from its own memory, so a computerd that restarts knows every live VM and counts it against the capacity at once. The unit's `KillMode=process` keeps more than the VMs: each running computer's forwarder (its only way out) and any open screen or guest connection stay up across an update, which is why systemd says "remains running after unit stopped" and "Found left-over process … Ignoring" on each restart. Those lines are expected. Hibernating every VM on each computerd update was the alternative; it was rejected: the spec has VMs outlive updates, and a hibernation writes and seals the VM's whole memory, minutes per computer on this server's disk.

**What a stopped VM leaves behind goes.** A computer's network namespace now goes when its VM does (stop, hibernate, a failed resume, the kill switch), not only when the computer is deleted; it is made again at every boot anyway. When computerd starts, before it takes a request, it removes every `magnus-<id>` namespace and every jail whose VM is not running. A jail can hold a memory snapshot in the clear when a hibernation was cut off, so it must not wait for that computer's next boot. Only a namespace named for a valid computer id is touched. The server had about 400 such namespaces (and as many `run-netns-magnus-*.mount` units) from computers stopped or deleted without `destroy`; the first start of this computerd clears them. Tests: `computers::sweep::tests`.

**Timing.** Every wake and hibernation logs how long each step took (`magnus-computerd: computer … resumed from its snapshot in … ms (open_snapshot …, launch …, restore …, reset …)`; `booted cold in … (new_overlay …, prepare …, launch …)`; `hibernated in … (snapshot …, seal …; N MiB of memory and state)`), and a wake's answer carries the same steps as `took_ms` for Magnus's log of the whole wake.
