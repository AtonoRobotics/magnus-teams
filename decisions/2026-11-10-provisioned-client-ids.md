# The release provisions each provider's client ID beside its secret

**Choice.** The release's "Provider secrets" step (`release/provision-registrations.sh`) provisions every provider in `catalog/registrations.toml` from the repository's pair of secrets, `<PREFIX>_CLIENT_ID` and `<PREFIX>_CLIENT_SECRET`, through a new control-socket route, `PUT /v1/admin/registrations/{provider}` (`{"actor", "client_id"?, "client_secret"?}`, in `crates/magnus/src/registrations.rs`). The client ID goes into the vault entry `registration_<provider>` with the secret. Sign-in uses the provisioned ID when there is one, and otherwise the catalog's. A public client (Microsoft, Vercel) gets its ID and is refused a secret. The owner setting or rotating a secret keeps the provisioned ID. A revoke removes the secret and keeps the ID, so a secret set again later still belongs to the same client.

Prefixes: google → `GOOGLE_DESKTOP` (the registration is `kind = "desktop"`, and the Google connectors sign in on a loopback address at any port, which only a desktop client allows); microsoft → `MICROSOFT`; github → `GH_OAUTH`; vercel → `VERCEL`; slack → `SLACK`; sentry → `SENTRY`. `GOOGLE_CLIENT_ID`, `GOOGLE_WEB_CLIENT_ID` and `MICROSOFT_TENANT_ID` are only compared with the catalog, never provisioned.

The step prints only "match", "differs" or "not set" for each repository client ID against the catalog's, and each provider's HTTP answer. It never prints a value. Values reach the kernel only through the environment and stdin. One provider failing does not stop the others, and the step fails at the end if any did.

**Reason.** magnus-teams is its own app with its own provider registrations, so its client IDs can differ from the catalog's compiled-in ones (which came from the owner on 2026-11-01). A secret only works with the client it was issued to. If the server sent the catalog's ID with the teams secret, the provider would refuse every token exchange. The spec has the server get client IDs per environment from outside the signed catalog ("the appliance getting client IDs from the relay", connectors spec rev 46). Until the relay exists, the vault, filled by the release, takes the relay's place, as it already does for the secret. Rewriting `catalog/registrations.toml` during the release was rejected for three reasons: the catalog is compiled in and signed, its IDs are shared with the magnus-claude lineage, and it would put a per-deployment value into the source. The log records only that a secret was set (`RegistrationSet`); a client ID alone records nothing new, and no event kind changes.

**Not provisioned.** The catalog connectors for GitLab, Hugging Face, Supabase, Cloudflare and Sentry use dynamic client registration (`registration = "dcr"`), and they connect today without any secret. They stay on it, even though the owner has a client with each of these providers. The reason is in `docs/remote-access-and-relay.md` ("Redirects to switch, later"): Sentry, Asana, GitLab, Hugging Face, Supabase and Cloudflare all require an exact redirect. Their clients are therefore usable only once the relay's one callback, `https://pyrallon.ai/v1/connections/callback`, answers, and "switching before the relay answers makes sign-in fail". The desktop's sign-in redirect is a loopback address with a port it picks at the time. Sentry's MCP server also has its own authorization server at `mcp.sentry.dev`, which does not take sentry.io's clients (`docs/connectors.md`, Client registration). Switching any of these now would turn a working connection into a broken one. The switch belongs with the relay cutover, and it should be made then.

**Discover.** The Apps page in this repository lists the server's connectors: the catalog's ten, plus any the organisation added (`GET /v1/connectors`). No registry of further entries exists here, and the teams server lists ten. There is therefore no Discover entry for a provisioned client to apply to. Asana and Shopify have no catalog connector. GitHub, Microsoft and Vercel have registrations but no connector yet, and Sentry's connector signs in by dynamic registration. Their clients are provisioned anyway, so they are ready when a connector uses them.
