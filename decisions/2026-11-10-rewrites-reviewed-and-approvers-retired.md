# A rewrite of a blocked message is reviewed again; workspace approvers are retired

Two parts of the old asks were still in the code after spec rev 140 ("Permissions and tasks"). Only four things reach the person: an action Auto Review judges outside what was asked, a payment every time, private data going to a new destination after untrusted input unless a rule covers it, and the person's own ask-first rule.

**A rewrite of a blocked message.** Before, a blocked message sent again unchanged stayed blocked, and a changed one went straight to the person as an ask. That came from `2026-11-09-safety-model-checks.md` and the older spec's "revised and resubmitted for approval". Rev 140 replaces every earlier approval rule, and a rewrite is not one of the four asks: no reviewer judged it outside what was asked. So a rewrite is now reviewed again, by the send reviewer when it is on and by Auto Review, like any boundary action. Each review is told that the message revises one that was blocked, and why it was blocked. It may pass, be blocked again, or be judged outside what was asked, which is the first ask. The same message sent again still stays blocked without a review. The agent is told: "a revised version is reviewed again, told why the first was blocked. The same message stays blocked."

The old rule had a reason: a reviewer that blocked once should not be the only judge of the rewrite. Rev 140 settles it for every action: Auto Review judges, and what it cannot judge asks. The rewrite still meets every check a first send meets: the floor, payments, the rule of two for private data after untrusted input, and the person's rules. The proposed invariant `a_blocked_message_goes_out_only_revised_and_approved` in `docs/proposals/agent-computer-safety-invariants.patch` and `agent-computer-all-invariants.patch` still expects the person's approval. It is not in `tests/invariants/` and was never applied. If the owner applies that patch, its last step needs to drop the approval.

**Workspace approvers.** A workspace admin could name who answers asks that used a resource (`POST /v1/workspaces/{ws}/approvers`), and the workspace view listed them. Rev 140 has only the asker answer: "In a team thread the card shows only to the person who asked." Nothing read the setting since the asks changed. The route, the field and the lookup are removed. The `approvers` change is an event kind, which is never deleted, so it stays and is read as nothing.
