# Local TOTP is the first embedded-auth slice (2026-11-07)

- #429 starts with the TOTP second factor on local password sign-in (spec test-plan unit item). Reason: it is the smallest slice that stands alone — purely additive (no enrolled secret means byte-identical behavior), so the live Keycloak and every Keycloak test stay green until the cutover, and it shares no files with the in-flight #425.
- TOTP-SHA1 on ring's HMAC plus a small base32, no new dependencies, proven by RFC 4648/6238 vectors. Reason: the HMAC itself stays ring's (no hand-rolled crypto), the truncation is ten lines of RFC arithmetic the vectors pin, and Cargo.lock stays untouched; a `totp-rs` dependency would buy nothing but supply chain.
- A missing code answers `NeedsCode` uncounted; a wrong code rejects and counts like a wrong password. Reason: mirrors the provider flow's forgive rule (needing the code says nothing was wrong) and the spec's "alike, and slowly" for wrong codes.
- The local `NeedsCode` answer reuses the provider's `code_needed` shape. Reason: the spec names the same `NeedsCode` screen for embedded sign-in, so the app changes nothing.
- Secrets live in `accounts/totp.json` (0600, beside the passwords), never in the log. Reason: a TOTP secret is a credential under invariant 2, stored exactly like the session token hashes.
- The owner's machine-code backup path does not ask for the authenticator code. Reason: the machine code is already that path's second factor; demanding TOTP there as well would break provider-down recovery for an enrolled owner.
